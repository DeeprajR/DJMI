# Module 2: Blood bank dashboard

**Status:** Built · 2026-09-06 · awaiting first run against PostgreSQL

## Goal

Close the loop the doctor app opens. A submitted request is answered from stock; what
stock cannot cover is handed to the donor bot (Module 3); the counter records what
actually happened. Keep every group at a configurable floor (25 units by default).

## What was built

### Repository

The dev branch had been left half-moved into `apps/hospital/`: `package.json`,
`tsconfig`, `next.config`, `src/components` and `src/proxy.ts` were there while
`src/app`, `src/db`, `src/lib`, `drizzle/` and `scripts/` stayed at the root, so neither
location built. Everything is back at the root, as every doc, script and the Drizzle
config already assumed. `apps/blood-connect/` was empty and is gone; Module 2 is a
role-gated section of this app under `/bank`, sharing auth, the design system and the
database client. Splitting it out later is mechanical.

### Role

`user_role` gains `blood_bank`. `src/lib/auth/bank-guard.ts` provides `requireBank()`
and `requireBankApi()`; admins pass, doctors do not (the bank decides on doctors'
requests and must not approve its own). `/bank/*` is protected in `src/proxy.ts`; the
app shell shows a bank navigation and a violet role badge there.

Provision an account: `npm run seed:bank -- --email … --password … --name …`.

### Tables (`drizzle/0002_blood_bank.sql`)

| Table | Purpose |
|---|---|
| `bank_settings` | One row: hospital identity donors see, district/city, floor per group |
| `blood_bags` | One row per bag; `rfid_tag` unique; `available → reserved/issued/discarded/expired` |
| `bank_decisions` | The bank's answer to a request: approved / partial / declined, units issued |
| `donor_demand` | Demand handed to the bot; the bot writes progress back |
| `donor_demand_confirmations` | Donors the bot confirmed; the counter marks the outcome |

Details of the last two — the contract with the bot — are in the bot repo's
`docs/integration.md`.

### Pages

| Route | Does |
|---|---|
| `/bank` | Stock per group against the floor, requests awaiting decision, recruitment in progress, one-click "recruit for groups below floor" |
| `/bank/inventory` | Add a bag (typed or scanned), filter by group/status, discard/restore |
| `/bank/requests` | Queue of submitted requests with stock on hand; decide, issue oldest-expiry bags, recruit for the shortfall |
| `/bank/demand` | Every demand with bot progress, the confirmed-donor roster, and Donated / No-show / Cancelled marks |
| `/bank/settings` | Hospital identity and the floor |

The doctor's request view (`/requests/:id/view`) now shows the bank's decision and, if
donors were recruited, how many are confirmed.

### Endpoints

Form POSTs under `/api/bank/*` follow the app's existing pattern (same-origin check,
role guard, Zod, redirect with a status code). `src/lib/bank/route-helpers.ts` holds
that pattern once.

`POST /api/bank/bags/scan` is the RFID reader's endpoint: JSON in and out,
authenticated by `X-Reader-Token` (`RFID_READER_TOKEN` in `.env`) since a reader has
no browser session. Actions: `lookup`, `stock`, `discard`. The hardware is out of scope;
this is the contract it talks to.

### Decision semantics (`src/lib/bank/demand.ts`)

`decideRequest` runs in one transaction: lock the oldest available bags of the group
(`FOR UPDATE SKIP LOCKED`), mark them issued to the request, record the decision, and
if there is a shortfall and the product is whole blood or packed RBC, insert a
`donor_demand` row. Platelets, plasma and cryo never recruit donors.

`raiseFloorDemand` inserts one `stock_floor` demand per group below the floor that has
no open floor demand already.

## Verification

`npm run typecheck`, `npm run lint`, `npm run build` pass (12 new routes). The
migration was generated by drizzle-kit and reviewed; it has not yet been applied to a
database, and the pages have not yet been exercised against one — that is the next
step once PostgreSQL credentials are available.

## Standing constraints kept

Frozen clinical wording untouched. Server-side identity: the bank user's id comes from
the session on every write. Immutability: a request already decided cannot be decided
again (`bank_decisions.blood_request_id` is unique). No self-registration: bank
accounts come from the seed script or the admin panel.

## Known gaps

- No bank UI for editing a bag's details after entry (only status changes).
- `reserved` bag status exists in the enum but nothing sets it yet.
- The admin panel's role dropdown does not yet offer `blood_bank`; use the seed script.
